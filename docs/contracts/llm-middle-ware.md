# [아카이브] 커스텀 벡터 데이터베이스 및 RAG 아키텍처 탐색 일지

## 1. 직접 vector db 를 만든다면?
- **사용자 질문**: 내가 직접 vector db 를 만든다면?
- **AI 답변 요약**:
  - 프로토타입이나 학습용으로 직접 만들 때 구현해야 할 핵심 요소:
    1. **핵심 인덱싱 알고리즘 (ANN)**: HNSW, IVF 등 근사치 탐색 알고리즘.
    2. **거리 및 유사도 측정**: 코사인 유사도, 유클리드 거리(L2) 계산 (NumPy/SciPy 활용).
    3. **데이터 저장소 및 영속성**: RAM 또는 디스크 기반 관리, 메타데이터 연동.
    4. **API 및 인터페이스**: FastAPI, gRPC 등을 통한 삽입/검색 엔드포인트 구축.

---

## 2. 파이썬과 RAM을 활용한 구현
- **사용자 질문**: py, ram 이용
- **AI 답변 요약**:
  - 파이썬의 `NumPy`와 인메모리(In-Memory) 구조를 활용한 가장 단순한 **Flat(Brute-force) 기반 벡터 DB** 프로토타입 코드 작성.
  - 벡터와 메타데이터, ID를 리스트/배열로 관리하며 코사인 유사도로 `top_k` 검색 수행.

---

## 3. 처음부터 HNSW 알고리즘 구현
- **사용자 질문**: 처음 부터 HNSW
- **AI 답변 요약**:
  - 다층 그래프 구조를 가진 **HNSW (Hierarchical Navigable Small World)** 핵심 뼈대 구현.
  - `HNSWNode` 클래스와 `SimpleHNSWDB`를 통해 멀티 레이어 구조 및 확률적 레벨 생성, 그리디(Greedy) 탐색 개념을 포함한 교육용 코드 제공.

---

## 4. 청크와 인덱싱 통합 모듈
- **사용자 질문**: 청크와 인덱싱 까지 한 모듈로 한다면?
- **AI 답변 요약**:
  - `sentence-transformers`(`all-MiniLM-L6-v2` 모델)를 활용하여 긴 텍스트 청킹 $\rightarrow$ 384차원 임베딩 변환 $\rightarrow$ HNSW 인덱싱까지 한 번에 처리하는 **End-to-End 인제스션(Ingestion) 모듈** 구성.

---

## 5. 임베딩 모델 차원 확인
- **사용자 질문**: model_name="all-MiniLM-L6-v2" 이 모델은 몇차원?
- **AI 답변 요약**:
  - `all-MiniLM-L6-v2` 모델의 임베딩 차원은 **384차원**. (작고 빠르며 로컬 프로토타입에 최적화된 80MB 내외의 경량 모델)

---

## 6. AWS 람다(Lambda) 및 S3 아키텍처 검토
- **사용자 질문**: 람다로 각 메소드별 API 로 분류하고, 최종 청크를 s3 에 저장해서 사용하다면?
- **AI 답변 요약**:
  - **S3**: 원문, 청크, 직렬화된 HNSW 인덱스 파일 보관.
  - **AWS Lambda**: API Gateway와 연동하여 적재(`POST /ingest`) 및 검색(`POST /search`) 처리.
  - **한계점**: 람다의 무상태(Stateless) 특성과 `Cold Start`로 인해, 요청마다 S3에서 인덱스를 다운로드해야 하는 지연 발생 및 동시 쓰기(Race Condition) 문제 지적.

---

## 7. EC2의 필요성 검토
- **사용자 질문**: 메모리 기반 warm start 의 ec2 가 절대 필요한가?
- **AI 답변 요약**:
  - 소규모/개인 프로젝트라면 Lambda + S3로도 가능하나, 데이터가 많아지고 수십 ms 단위의 빠른 응답과 상시 메모리 유지(Warm State)가 필요하다면 **EC2, ECS(Fargate)** 같은 상시 구동 서버가 훨씬 유리함을 설명.

---

## 8. LLM 부재 시 대화의 부자연스러움
- **사용자 질문**: llm 모델 없이 대화가 부자연스러우면?
- **AI 답변 요약**:
  - 벡터 DB는 관련 청크를 찾아주는 "사서"이고, LLM은 자연스럽게 문장으로 엮어주는 "작가"이므로 LLM이 없으면 단편적인 문장 조각만 던져지게 됨.
  - 추출형 QA 템플릿 적용, 하이브리드 검색, 경량 로컬 LLM(SLM) 도입 등으로 보완 가능.

---

## 9. 토큰 및 크레딧 비용 비교 (통째로 넣기 vs RAG)
- **사용자 질문**: 처음부터 질의응답하는 OpenAI key 를 붙인것과 기업형 소규모로 RAG 기본 모델 만든뒤 openai key 붙이는 것과 대략적인 토큰, 크레딧 차이는?
- **AI 답변 요약**:
  - **통째로 넣기(Naive)**: 질문할 때마다 문서 전체 토큰이 입력되어 비용 폭탄 발생 및 Context Window 한계 직면.
  - **소규모 RAG 구축**: 문서 전체는 벡터 DB에 두고, 질문과 연관된 상위 핵심 청크(수백 토큰)만 LLM에 전달하므로 **비용이 획기적으로 절감(센트 단위)**되며 데이터가 늘어나도 비용 유지.

---

## 10. 토큰 정제 미들웨어 및 상용 솔루션 현황
- **사용자 질문**: openai key 사용 중간에 토큰 정제 미들웨어를 만들면? 현재 이런 기능의 솔루션이 나온게 있나?
- **AI 답변 요약**:
  - API 호출 전단에서 비용과 지연 시간을 줄여주는 미들웨어/프록시 솔루션 존재.
  - **의미적 캐싱(Semantic Cache)**: `GPTCache` 등 (유사 질문은 캐시된 답변으로 응답하여 토큰 비용 0화).
  - **컨텍스트 압축 및 프록시 게이트웨이**: `LiteLLM`, `Portkey` 등 (프롬프트 압축 및 드롭인 연동).
